# 请求参数与缓存

## 请求参数

发给模型的参数（输出上限、温度、思考开关等）写在预设最上方的“请求参数”里，**用当前协议原生的字段名**，合并进请求体：

```
// 关闭思考，输出上限 4096
thinking: { "type": "disabled" },
max_tokens: 4096,
temperature: 1
```

写法比标准 JSON 宽松：

- 最外层的花括号可以省略。
- 字段名可以不加引号。
- 允许末尾多一个逗号，`//` 之后是注释。

但**字段之间必须有逗号**。漏了逗号会标出第几行第几列，改好之前不能保存。

### 平台固定的字段

模型名、消息、系统提示、流式输出这些每次请求都一样的字段由平台填写，不能写在这里：`model`、`messages`、`input`、`contents`、`system`、`systemInstruction`、`stream`、`stream_options`。

### 自动补上的字段

当前协议必需的字段没写时会自动补上，例如 Claude 必需的 `max_tokens: 4096`。打开编辑时会补进草稿，你可以直接改数值；如果换了模型、协议变了，发送时也会按默认值补上。

### 各协议常用字段

| 协议 | 输出上限 | 其他 |
|---|---|---|
| OpenAI Chat | `max_tokens` 或 `max_completion_tokens` | `temperature`、`top_p`、`reasoning_effort` |
| OpenAI Responses | `max_output_tokens` | `temperature`、`reasoning: { effort: "low" }` |
| Claude | `max_tokens`（必需） | `temperature`、`thinking: { type: "enabled", budget_tokens: 2048 }` |
| Gemini | `generationConfig: { maxOutputTokens }` | `generationConfig: { temperature, thinkingConfig: { thinkingBudget } }` |

字段写错时，上游会返回错误并显示在对话里。发送前可以在预览的“请求体”里核对。

## 缓存

模型服务商会缓存请求开头不变的部分，命中缓存的部分更便宜、更快。SkyTavern 的分区就是按这个设计的：正文前保持不变，会变化的内容放到正文后或 Dx。

每条回复下面会显示上游报告的用量，其中“缓存命中”就是被复用的部分，可以直接看出缓存有没有生效。

### 断点

预设设置（齿轮按钮）里选择缓存断点的模式：

- **自动**：放两个断点，一个在正文前的末尾，一个在第一条易变消息之前（Dx 词条、被插入规则改过的聊天记录、正文后）。
- **手动**：用“缓存断点”类型的预设词条自己指定位置，可以带 IF。断点落在它前面那条消息上。

各协议的处理方式：

- Claude：落成 `cache_control`，最多 4 个，超出时保留最后 4 个。
- OpenAI：自动前缀缓存，不需要断点。
- Gemini：目前依赖隐式缓存，前缀相同时自动命中。

### 什么会让缓存失效

- 正文前的词条内容变了，包括 IF 结果变化、用了 `{{hp}}`、`{{$time}}` 这类会变的占位符。
- 插入规则改了聊天记录中间的消息。
- 切换预设或模型。

风险检查会提示前两种情况，见[请求结构](request-structure.md#风险提示)。

## token 预估

预览、左栏和正文裁剪里的 token 数都是**发送前的预估**，按模型选用对应的分词器来数。

### 按模型名选分词器

模型名用**部分匹配**：先转小写，去掉 `anthropic/`、`models/` 这类前缀和 `:free` 这类后缀，再按下表从上往下匹配，第一条命中的生效。所以 `anthropic/claude-opus-4.7`、`claude-opus-4-7@20260416` 这些渠道里的写法都能认出来。

| 模型名里有 | 分词器 | 准确度 |
|---|---|---|
| `claude`：4.7 及以后、5.x、mythos、fable | Claude 新一代 | 近似 |
| `claude`：4.6 及以前 | Claude 旧一代 | 近似 |
| `gpt-4o`、`gpt-4.1`、`gpt-5`、`o1`/`o3`/`o4`、`gpt-oss` | OpenAI o200k | 精确 |
| `gpt-4`、`gpt-3.5` | OpenAI cl100k | 精确 |
| `gemini`：3 及以后 | Gemma 3 词表 | 近似 |
| `gemini`：2.x 及以前 | Gemma 3 词表 | 近似 |
| `gemma` | Gemma 3 | 精确 |
| `deepseek`：带 v3 / r1 | DeepSeek V3 | 精确 |
| `deepseek`：其他 | DeepSeek V4 | 精确 |
| `qwen`、`qwq` | Qwen 3 | 精确 |
| `llama` | Llama 3 | 精确 |
| `mistral` 等 | Mistral Tekken | 精确 |

这是默认的“**模型名优先**”。系统设置 → token 预估里可以改成“**接口类型优先**”：Claude 接口一律用 Claude 分词器、Gemini 接口一律用 Gemini 分词器（新旧代仍按模型名里的版本号分），OpenAI Responses 一律用 o200k，只有 OpenAI Chat 这种通用接口才看模型名。Azure 这类部署名和模型无关的渠道适合用它。

模型名优先时，都没匹配到就按协议兜底：Claude 协议用 Claude 新一代，Gemini 协议用 Gemini 3，OpenAI Responses 用 o200k，OpenAI Chat 用 **DeepSeek 作参照**（GLM、Kimi、豆包等没有公开分词器的模型都走这一条）。

渠道名实在认不出时，在模型配置里把“分词器”从“自动”改成指定的一个。

> Claude 没有公开分词器，只能近似；4.7 起换了分词器，同样的文字多出约 1.0–1.35 倍 token，所以分成两代，新一代默认先乘 1.3。

### 按实际用量校准

每次回复，上游都会报告真实的输入 token 数。SkyTavern 把**当时的模型、分词器、预估多少、实际多少**记在这条回复上，之后：

- 校准系数 = 最近几次（最多 5 次）同一模型、同一分词器的“实际总和 ÷ 预估总和”，乘到预估上。
- 优先用本会话的记录；新会话还没有记录时，用这个账号最近其他会话里同一模型的记录。
- 系数限制在 0.5 到 2.5 之间，个别离谱的值（例如渠道报错的用量）不会把预估带偏太多。

所以近似的分词器用几轮之后也会很接近真实值。实际值按协议计算：Claude 的输入要加上缓存命中和缓存写入的部分。

### 在哪里看

- **预览顶部**：总 token 数，旁边标出校准情况。悬停可以看到用了哪个分词器、为什么选它。
- **左栏每个词条**：右边的小数字是这个词条的 token。进入了请求的按它这次形成的消息算（占位符已展开），没发送的按词条内容算。
- **每条回复下面**：上游报告的用量旁边是发送前的“预估”，悬停可以看偏差。

分词器第一次使用时要加载词表（零点几秒到两秒），之后常驻。词表没装好或加载失败时退回粗略估算，预览里会提示。

## 正文裁剪

预设设置里的“输入上限”（token）是平台自己的预算，不发给模型，按上面的预估（校准后）判断。超过上限时：

- 只从聊天记录的**最前面**整条删除，最新一条永远保留。
- 一次腾出大约 5 轮的空间，而不是每轮删一点。这样接下来几轮的开头保持不变，缓存才能继续命中。轮数在预设设置里改（1–50）：越多，裁一次之后能撑越久，缓存越稳，但一次丢掉的内容也越多。
- 裁剪的起点会记下来，下一轮沿用；切换预设或模型后重新计算。

最新一条加上必需的提示词仍然超出上限时，不会发送，并提示原因。
